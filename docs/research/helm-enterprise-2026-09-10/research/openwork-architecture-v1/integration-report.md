# OpenWork executable architecture at the pinned revision

**Recommendation:** reuse selected MIT desktop/server mechanisms through explicit adapters, preserve Helm’s actual OpenCode fork, and implement Hades-owned orchestration/acceptance above it. The inspected OpenWork code contains substantive engine, recovery, browser and policy mechanisms; adopting its interface alone would miss them. Enterprise server components require a separate licensing decision.

**Scope and status:** pin `88b1eec4aa8bddd7a8abccbb39285c41bd1c7c36`, development snapshot, source extraction **needs independent review**. Forty-three complete connector-returned bodies are retained and verified against the previously acquired untruncated Git tree. No source execution, dependency installation, service launch, credentials or permission bypass occurred. This is broad path tracing, not an exhaustive security audit, released-binary acceptance, measured superiority claim or a governed-packet acceptance.

Preserve copyright and notices, examine transitive dependencies and adapt rather than blindly importing process-global state.
- **Restricted implementation references:** ee/apps/den-api automation authority/executor, MCP auth and entitlements. No blanket MIT reuse. Implement behavior independently from requirements or obtain applicable rights.
- **Not yet classified:** all third-party bundles, actual release sidecar versions, full client-side carve-out applicability, subscription-defined Enterprise Features and downstream deployment terms. No service was deployed or license entitlement changed.

There are real limits to the guarantees in these paths, not proof of repository-wide defects:

1. Task recovery intentionally declines delegated/blocked/unknown cases and only reloads running records. It avoids automatic duplicate continuation, but its prompt asking the model not to repeat effects is not a durable external-effect ledger. Test manual reconciliation after a claimed-but-unacknowledged send.
2. The registry write queue and task journal are process-local coordination around durable files/rows. Desktop main requests Electron’s single-instance lock; this does not by itself prove exclusive ownership across CLI/server processes or different profiles pointed at the same data directory. The source does not support a universal multi-host fencing claim.
3. Engine promotion can proceed after standby preparation failed. Treat provider-ready, policy-ready and engine-listening separately; this is a visible branch, not an inferred outage.
4. UI mailbox requests expire and disappear in memory. Timeout does not revoke work already delivered. The desktop discovery file writes a bearer token without an explicit file mode in that call; actual parent-directory/umask protections were not assessed. Require private discovery files and typed uncertain outcomes in Helm.
5. The cloud success branch exports a transcript and synthesizes a result from assistant text or a generic completion fallback. This is engine settlement, not independent artifact/test acceptance. Build an evidence gate above it.
6. Browser DOM observations cover the top document with bounded element/text output; frame/canvas actions need separate image/control handling. Sensitive labels/text elsewhere on a page are not generally scrubbed by the password-target check. A claim of complete secret filtering is unsupported.

## Prioritized measurable parity and differentiation checks

These are proposed Hades/Helm checks to reconcile with the local audit, not claims those features are absent.

| Priority | Check | Acceptance evidence |
|---|---|---|
| P0 | Provider and policy readiness | Engine responds but credentials missing, identity revoked, or policy unavailable: no task admission; UI names the distinct blocker. |
| P0 | Durable ownership and uncertain effects | Crash before/after dispatch and before/after acknowledgement; restart produces one execution or explicit unknown, never blind duplicate. Two processes sharing storage cannot both own the same attempt. |
| P0 | Whole-tree cancellation | Parent, child provider, browser action and pending approval stop together; later child completion cannot settle a replacement attempt. Retained receipt shows each stop/unknown outcome. |
| P0 | Artifact acceptance above transcript | Worker says done with broken tests or no expected file: product remains review-needed/failed; evidence binds exact source SHA, diff and command exit output. |
| P1 | Busy engine configuration rollover | Change provider/MCP/skill/policy during two running sessions; new task sees new config, old task retains documented generation, failed standby never strands work. |
| P1 | Authority revocation | Revoke owner/model/connector/website grant during provisioning, approval and reattachment; next side effect is denied. Stored thread approval cannot restore revoked authority. |
| P1 | Browser fidelity | Mutate DOM/viewport, navigate frame, change screenshot or switch conversation during approval: action refuses. Approved input reports dispatched/unverified until fresh result observation. |
| P1 | Local/cloud workflow handoff | Preserve task/attempt/workspace/artifact provenance and permission boundaries across Hades, Helm and Browser; caller can reconcile a lost handoff acknowledgement. |
| P1 | Schedule lifetime clarity | Close laptop or kill scheduler with a due run: documented local/cloud behavior, missed-run policy, stable occurrence ID, original owner revalidation and one admitted run. |
| P2 | Usable policy and evidence controls | Show winning policy layer, granted scope, model usage, blockers, review evidence and safe recovery from one task detail view. |
| P2 | Cross-provider equivalence | Run the same bounded task and failure matrix through actual Codex/Claude/OpenCode/Gemini/Grok adapters; unsupported semantics remain explicit. No uniform support inferred from a terminal wrapper. |
